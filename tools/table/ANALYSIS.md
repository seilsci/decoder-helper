## 2. 이론상 최선과의 차이

- **방법**: 현재 모델을 정답 분포로 놓았습니다. 현재 앱의 정책 π(main 표, 표에 없으면 main 가중치의 롤아웃)에 대해 V^π를 정확히 계산했습니다. π' = 각 상태에서 Q^π(s, t) = 1 + Σ 결과 확률 × V^π(다음 상태)가 가장 작은 칸, 즉 지금 앱 위에 한 단계 더 내다보는 탐색입니다.
- **추정식**: 성능 차 보조정리로 V^π − V^π' = E_{π'}[Σ(Q^π(s, π(s)) − min_t Q^π(s, t))]입니다. 이 값을 1000판(✕ 쌍 빈도대로 9쌍에 배분, 당첨은 현재 모델로 뽑음)에서 정확히 평균했습니다. 판별 클릭이 아니라 기대값 차이의 합이라 잡음이 작습니다.

| 항목 | 값 |
|---|---|
| main 앱의 정확한 기대 클릭(현재 모델 기준, 쌍 빈도 가중) | **9.384** (쌍별 9.333 ~ 9.460) |
| 보류 커밋 앱(303판 + 좌우 계수 표)의 정확한 기대 클릭 | **9.337** (main보다 −0.047) |
| main 앱 → π'(한 단계 더 내다봄) 개선 | **0.030클릭/판** |
| π'가 앱과 다른 칸을 고른 횟수 | 판당 1.62번 |
| 구간별 개선: 1~3번째 수 | 0.003 |
| 구간별 개선: 4~8번째 수 | **0.020** |
| 구간별 개선: 9~12번째 수 | 0.007 |
| 구간별 개선: 13번째 수 이후 | 0.000 |
| π' 계산 시간 | 결정 4088개(같은 상태 재사용 제외), 평균 5.3초, 최대 25분(첫 수, 9개 동시 실행 중). 앱은 수당 수 ms ~ 수백 ms |

- **판정**: 0.030 ≤ 0.05이므로 탐색 강화는 불필요합니다. 손해가 가장 큰 곳은 4~8번째 수입니다. 0.030 중 일부는 main 표가 옛 모델 기준이라 생긴 몫입니다. 보류 커밋 표가 이 중 일부를 이미 회수했습니다(9.384 → 9.337).
- **주의**: π'는 한 단계 개선이므로 이론상 최선과의 차이는 **0.030 이상**입니다. 정책 반복은 보통 첫 단계에서 개선의 대부분이 나오지만, 정확한 최선값은 상태 수 때문에 계산하지 못했습니다.

명령: `node analysis/opt.js <x> <판 수> main` (쌍마다 따로 실행. 이번에는 106/83/112/109/96/92/106/112/185판)
